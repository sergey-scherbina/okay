# okay-x402: paying for an HTTP (or MCP) resource with a chain payment

## Overview

x402 (Coinbase et al., spec v2 read from the local clone
`../crypto/x402/specs/x402-specification-v2.md`) revives HTTP 402
Payment Required as a protocol:

1. a client requests a resource;
2. the server answers `402` with a `PAYMENT-REQUIRED` header
   (base64 JSON `PaymentRequired`: resource, and `accepts`, a list of
   `PaymentRequirements` — scheme, CAIP-2 network, amount in atomic
   units as a DIGIT STRING, asset, payTo, maxTimeoutSeconds, extra);
3. the client repeats the request with `PAYMENT-SIGNATURE` (base64 JSON
   `PaymentPayload`: the accepted requirements plus a scheme-specific
   signed authorization — for `exact` on EVM an EIP-3009
   `transferWithAuthorization` signed with EIP-712);
4. the server verifies and settles, usually through a FACILITATOR
   (`POST /verify`, `POST /settle`, `GET /supported`), and answers with
   `PAYMENT-RESPONSE` (base64 JSON `SettlementResponse`: success,
   transaction id, network, payer).

Transports: HTTP (the original), MCP and A2A. okay has an HTTP server
and client (okay-http) and MCP (okay-mcp), and an agent runtime
(okay-agent) that is exactly x402's "AI agent pays for a tool" case.

The operator: "may be needed". This spec says what supporting it means
in okay and in what order, so it is ready when it is.

## Design

### 1. Types, from the one Schema

`PaymentRequired`, `PaymentRequirements`, `ResourceInfo`,
`PaymentPayload`, `SettlementResponse`, `VerifyResponse`,
`SupportedResponse` as case classes with derived `Schema`s. Fields
line up with okay-chain and okay-codec as they are:

- `network: Network` (okay-chain, CAIP-2 — x402 v2's own format);
- `amount: BigInt` — `Schema.SBigInt` writes a digit string, which is
  x402's wire form for amounts, byte for byte;
- `asset`, `payTo`: strings, interpreted against the network
  (`Account`/`Asset` views where the network is known);
- `payload` and `extra`: scheme-specific, carried as `Json` until a
  scheme module types them.

Header codec: base64 of the JSON (okay-codec's `Base64` + `Json`).
Golden tests: the base64 headers printed in x402's
`transports-v2/http.md` decode to the documented objects and encode
back to the same bytes.

### 2. Server side: a 402 gate in okay-http

A route wrapper: given the requirements for a route, a request with no
`PAYMENT-SIGNATURE` gets `402` + `PAYMENT-REQUIRED`; a request with one
is verified and settled through a `Facilitator`, and the handler runs
only on success, with `PAYMENT-RESPONSE` on the answer.

- `Facilitator` is a trait (`verify`, `settle`, `supported`); stage 1
  ships the HTTP client for a remote facilitator. Verifying `exact`
  ourselves needs keccak-256 + secp256k1 recovery + EIP-712, none of
  which okay-crypto has today (checked 2026-09-23) — so local
  verification is its own stage, not assumed.
- Settlement is a chain transaction: `SettlementResponse.transaction`
  is a `TxId` on `network`. Where the server wants more than the
  facilitator's word, okay-chain's `Tracker` follows that transaction
  to the finality the server requires — the read side this module
  already has.
- Replay: x402 relies on the authorization nonce and the token
  contract; the gate additionally refuses a payload it has already
  settled (an idempotency record keyed by the payload), so a retried
  request is not charged twice.

### 3. Client side: paying from okay-http and okay-agent

A client wrapper that sees a `402`, picks one of `accepts` by a policy
(network, asset, max amount — never "pay whatever is asked"), asks a
`Payer` for the signed payload, and repeats the request. `Payer` is a
trait; signing keys never enter okay-x402. For an agent: a tool call
that hits 402 surfaces the price to the agent's policy before paying.

### 4. MCP

x402's MCP transport carries the same objects in MCP messages instead
of headers; after HTTP works, okay-mcp tools can declare a price the
same way. Stage 3.

## Stages

- **Stage 0** — [x] types + header codec + golden tests from the spec's
  own examples (needs okay-chain stage 0 for `Network`).
- **Stage 1** — [x] okay-http server gate over a remote `Facilitator`;
  client wrapper with a payment policy and a `Payer` trait; an
  end-to-end test against a fake facilitator.
- **Stage 2a — local `exact`/EVM verification** (x402-exact-local,
  operator: "Продолжай 402"): a JVM satellite module `okay-x402-evm`
  (BouncyCastle for keccak-256 and secp256k1, as okay-security-argon2
  carries its own), so okay-x402 itself stays dependency-free and
  cross-built.
  - [x] keccak-256, secp256k1 public-key RECOVERY (low-s, v 27/28, as
        USDC's FiatToken requires), an Ethereum address from a key
  - [x] EIP-712 for EIP-3009's `TransferWithAuthorization`: the domain
        from `extra.name`/`extra.version`, `chainId` from the CAIP-2
        network, `verifyingContract` = the asset
  - [x] `ExactEvm.verify`: the signature recovers to `authorization.from`;
        `to` = `payTo`; `value >= amount`; `validAfter <= now`;
        `validBefore >= now + 6` (the reference's block-time margin); an
        eip155 network — with the REFERENCE implementation's
        `invalidReason` codes, so a refusal reads the same everywhere
  - [x] `LocalFacilitator`: verify locally, then (optionally) remotely;
        settle through the remote one (broadcasting needs a node)
  - [x] tests: known keccak vectors; private key 1 → its known address;
        EIP-712's own `Ether Mail` domain separator; the x402 spec's
        example signature recovering to its `from`; sign-and-recover
  - NOT offline, stated: the payer's BALANCE and the call SIMULATION
    (steps 2 and 5 of the scheme) need an RPC; smart-wallet signatures
    (EIP-1271/6492) need the chain too.
- **Stage 2b — settlement followed with okay-chain `Tracker`**: needs an
  EVM chain source, and okay has none (okay-watch's is not to be moved
  while its publication is undecided). Deferred until there is one.
- **Stage 3 — the MCP transport** (x402-mcp; x402
  `specs/transports-v2/mcp.md`). Prerequisite landed as mcp-error-data:
  `Rpc.Failed` carries JSON-RPC `error.data`, `Session.requestRpc`
  answers a refusal whole.
  - [x] okay-mcp: `Server.Around[G]`, a hook around EVERY request in
        `serveIn` — answer now (`Left`), or pass on with a `leave` that
        sees the reply; `Around.none` is the old server exactly
  - [x] okay-x402: `Charge` (admit = match → claim → verify; settle;
        release) — the transport-neutral half of `Gate`, which now uses it
  - [x] okay-x402-mcp (JVM+JS): `X402Mcp.gate` — 402 with the
        `PaymentRequired` in `error.data`; the payment from
        `params._meta["x402/payment"]`; a malformed one -32602; the
        receipt into `result._meta["x402/payment-response"]`; a tool
        answering `isError` is not charged; a failed settlement is a 402
        with the settlement beside the requirements
  - [x] `X402Mcp.byTool` prices `tools/call` by name, resource
        `mcp://tool/<name>` as the transport's examples
  - [x] `X402Mcp.Paying`: a Session that pays a 402 once by policy and
        payer and repeats the request with `_meta`
  - [x] tests: the transport spec's three examples read, and its 402
        written byte for byte; every gate road as a pure stage; client
        and server over an in-memory wire
- **Stage 3b — for an agent** (x402-agent; §3's "surfaces the price to
  the agent's policy before paying"):
  - [x] `Consent` in okay-x402: asked about the ONE chosen requirement
        with the resource, after `Policy` and before the `Payer`; told
        (`returned`) when an approved payment was not taken — refused,
        declined, or answered without a successful settlement
  - [x] `Consent.ask` (a person, a model), `Consent.budget` (a running
        total per network and asset, reserved atomically), `a and b`
        (the second's refusal returns the first's reservation)
  - [x] both paying clients take it: `Paying(http, policy, payer,
        consent)`, `X402Mcp.Paying(session, policy, payer, consent)`
  - [x] `X402Mcp.Paying.interpret` / `.handler`: the paying session as
        the agent's `Tool` handler — the same agent program against a
        free table and a paid MCP server gives the same answer
- **Stage 4 — hardening: keys, limits, memory, settings** (x402-hardening,
  operator: "А как насчет безопасности и вобще настроек? Подписи и тд" →
  "Делай"). What stage 3b left a user to build by hand:
  - [ ] `Signer` (okay-x402-evm): the key behind ONE operation, `sign(digest)`
        plus its `address` — a KMS, an HSM or a remote wallet implements
        it; `Signer.local(key)` is for development and says so
  - [ ] `EvmPayer(signer, clock, nonces)`: the `exact`/EVM payload as the
        reference client builds it (coinbase/x402 typescript
        mechanisms/evm/src/exact/client/scheme.ts): `validAfter = now − 600`,
        `validBefore = now + maxTimeoutSeconds`, a random 32-byte nonce;
        refuses requirements it cannot sign honestly (not `exact`, not
        eip155, no EIP-712 domain in `extra`); its payload VERIFIES under
        `ExactEvm.verify` — the round trip is the test
  - [ ] `Policy` gains `and` and `Policy.payTo(addresses)`: without a
        recipient allowlist a hostile server directs the payment to any
        address inside the limit; `Consent.resources(pred)` limits by the
        resource (host, path)
  - [ ] `Consent.paid(choice, settlement)`: told the settlement of every
        payment that WAS taken — the audit needs the transaction
  - [ ] `PaymentJournal`: every decision as a record (asked, refused,
        reserved, returned, paid with its transaction; claimed/released on
        the server) — `PaymentJournal.inMemory`, and `on(topic)` over an
        okay-persist `Topic`, so it survives a restart; `Consent.audit`
  - [ ] `Budget` over a journal: its state is the FOLD of its own records,
        so a restart does not refill it; an optional WINDOW (a daily cap)
        counts only reservations inside it
  - [ ] `Settled.journaled(journal)`: the server's replay record survives
        a restart too
  - [ ] `HttpFacilitator` takes request headers per call (an API key, a
        fresh JWT) — a hosted facilitator wants authentication
  - [ ] `X402Conf` (okay-conf): policy, budget, recipients, resources and
        the facilitator (URL + `Secret` reference) as a config file with
        secrets as references; `X402Conf.client` builds the `Policy` and
        `Consent`, `X402Conf.facilitator` the authenticated facilitator
- A Cardano scheme only if x402 defines one (it has `exact` for EVM,
  SVM, Aptos, Sui as of the local clone) — not yet.

## Decisions

- 2026-09-23 — **the codec is hand-written over `Json`, not a derived
  `Schema`.** x402 carries open JSON (`payload`, `extra`, `extensions`)
  and `Schema` has no case for an arbitrary JSON value; and x402 OMITS
  absent optionals where a derived encoder writes `null`.
- 2026-09-23 — **settle AFTER the route, and only a 2xx.** Settling
  first takes a payment for a failure; delivering before settling gives
  the resource away if settlement fails. The gate runs the route, keeps
  its answer, settles, and returns the answer only on success.
- 2026-09-23 — **replay is an atomic claim** on the payload, released
  when verification, the route or settlement fails — so a retry of an
  honest failure is not refused as a replay.

- 2026-09-23 — x402 sits ON okay-chain rather than beside it: its
  network, asset and amount types are okay-chain's, and confirming a
  settlement is the follower's job.
- 2026-09-23 — facilitator first, local verification later: the
  primitives for `exact`/EVM (keccak, secp256k1, EIP-712) do not exist
  in okay yet.

- 2026-09-23 — **the MCP hook is at the REQUEST, not at the tool.**
  `ToolCall` drops `_meta`, where the payment travels, and the transport
  spec prices any request (`initialize`, `resources/read`), so a
  tool-level wrapper could neither read the payment nor price the rest.
  And it is ONE hook returning a `leave` closure rather than a
  before/after pair: what `before` learned (the admitted payment) is
  exactly what `after` must settle, and a pair would need a table keyed
  by request id to carry it across.
- 2026-09-23 — **a separate `okay-x402-mcp`**, so okay-x402 does not
  pull okay-agent through okay-mcp (okay-watch wants x402 without an
  agent runtime), and okay-mcp knows nothing of payments.
- 2026-09-23 — **MCP's "not delivered" is `isError`**, as HTTP's is a
  non-2xx: a tool that answered its own failure is not charged, and its
  payment is released for the retry.
- 2026-09-23 — **`Consent` beside `Policy`, not instead of it.**
  `Policy` is a predicate over every offered requirement and picks one;
  a consent is asked about the one picked and may be slow (a person) or
  stateful (a budget). Folding the budget into `Policy` would have made
  choosing a requirement SPEND money, before the payer had even signed.
  A budget RESERVES on approval and is given back on every road that did
  not end in a successful settlement, so two racing calls cannot both
  spend its last units and a refusal costs nothing.
- 2026-09-23 — **a malformed payment is -32602, not 402**, following
  the transport spec's error table — unlike the HTTP gate, where there
  is no other status to say it with.

## Results

- Stage 3b (2026-09-23, x402-agent): 4 consent tests in okay-x402
  (JVM and JS) and 3 agent tests in okay-x402-mcp (JVM). A refused
  signature and an unsettled payment both leave a budget where it
  started; `budget and ask(no)` spends nothing.

- Stage 3 (2026-09-23, x402-mcp): okay-x402-mcp, 17 tests on the JVM
  (12 on JS, where the wire tests do not run). The spec's paid
  `tools/call`, its settled answer and its 402 all read, and the 402 is
  written back byte for byte. The HTTP gate's own suite passes
  unchanged over the extracted `Charge`.

- Stage 2a (2026-09-23, x402-exact-local): okay-x402-evm, 7 tests. The
  x402 specification's example payment — a real EIP-3009 signature on
  Base Sepolia USDC — recovers to its `from` through our keccak,
  EIP-712 and secp256k1 recovery, and verifies inside its window;
  keccak vectors, private key 1's address and EIP-712's `Ether Mail`
  domain separator match; every refusal carries the reference
  implementation's code. One expectation of the test's own draft was
  wrong and the code right: `payTo` is NOT in the signed message, so a
  different `payTo` still recovers and fails the RECIPIENT check.

- okay-x402 landed stages 0–1 (2026-09-23), JVM and JS, 14 tests:
  the four headers of transports-v2/http.md decode and re-encode to
  the same JSON; the gate end to end in memory (unpaid 402, paid 200
  with `PAYMENT-RESPONSE`, a replay refused, the policy's limit, an
  invalid signature, a failing route not settled, a failed settlement
  withholding the answer); `HttpFacilitator` against a service built
  from the protocol's own shapes, an unreadable answer a refusal.
