# okay-x402: paying for an HTTP (or MCP) resource with a chain payment

## Overview

x402 (Coinbase et al., spec v2 read from the local clone
`../crypto/x402/specs/x402-specification-v2.md`) revives HTTP 402
Payment Required as a protocol:

1. a client requests a resource;
2. the server answers `402` with a `PAYMENT-REQUIRED` header
   (base64 JSON `PaymentRequired`: resource, and `accepts`, a list of
   `PaymentRequirements` — scheme, CAIP-2 network, amount in atomic
   units as a DIGIT STRING, asset, payTo, maxTimeoutSeconds, extra);
3. the client repeats the request with `PAYMENT-SIGNATURE` (base64 JSON
   `PaymentPayload`: the accepted requirements plus a scheme-specific
   signed authorization — for `exact` on EVM an EIP-3009
   `transferWithAuthorization` signed with EIP-712);
4. the server verifies and settles, usually through a FACILITATOR
   (`POST /verify`, `POST /settle`, `GET /supported`), and answers with
   `PAYMENT-RESPONSE` (base64 JSON `SettlementResponse`: success,
   transaction id, network, payer).

Transports: HTTP (the original), MCP and A2A. okay has an HTTP server
and client (okay-http) and MCP (okay-mcp), and an agent runtime
(okay-agent) that is exactly x402's "AI agent pays for a tool" case.

The operator: "may be needed". This spec says what supporting it means
in okay and in what order, so it is ready when it is.

## Design

### 1. Types, from the one Schema

`PaymentRequired`, `PaymentRequirements`, `ResourceInfo`,
`PaymentPayload`, `SettlementResponse`, `VerifyResponse`,
`SupportedResponse` as case classes with derived `Schema`s. Fields
line up with okay-chain and okay-codec as they are:

- `network: Network` (okay-chain, CAIP-2 — x402 v2's own format);
- `amount: BigInt` — `Schema.SBigInt` writes a digit string, which is
  x402's wire form for amounts, byte for byte;
- `asset`, `payTo`: strings, interpreted against the network
  (`Account`/`Asset` views where the network is known);
- `payload` and `extra`: scheme-specific, carried as `Json` until a
  scheme module types them.

Header codec: base64 of the JSON (okay-codec's `Base64` + `Json`).
Golden tests: the base64 headers printed in x402's
`transports-v2/http.md` decode to the documented objects and encode
back to the same bytes.

### 2. Server side: a 402 gate in okay-http

A route wrapper: given the requirements for a route, a request with no
`PAYMENT-SIGNATURE` gets `402` + `PAYMENT-REQUIRED`; a request with one
is verified and settled through a `Facilitator`, and the handler runs
only on success, with `PAYMENT-RESPONSE` on the answer.

- `Facilitator` is a trait (`verify`, `settle`, `supported`); stage 1
  ships the HTTP client for a remote facilitator. Verifying `exact`
  ourselves needs keccak-256 + secp256k1 recovery + EIP-712, none of
  which okay-crypto has today (checked 2026-09-23) — so local
  verification is its own stage, not assumed.
- Settlement is a chain transaction: `SettlementResponse.transaction`
  is a `TxId` on `network`. Where the server wants more than the
  facilitator's word, okay-chain's `Tracker` follows that transaction
  to the finality the server requires — the read side this module
  already has.
- Replay: x402 relies on the authorization nonce and the token
  contract; the gate additionally refuses a payload it has already
  settled (an idempotency record keyed by the payload), so a retried
  request is not charged twice.

### 3. Client side: paying from okay-http and okay-agent

A client wrapper that sees a `402`, picks one of `accepts` by a policy
(network, asset, max amount — never "pay whatever is asked"), asks a
`Payer` for the signed payload, and repeats the request. `Payer` is a
trait; signing keys never enter okay-x402. For an agent: a tool call
that hits 402 surfaces the price to the agent's policy before paying.

### 4. MCP

x402's MCP transport carries the same objects in MCP messages instead
of headers; after HTTP works, okay-mcp tools can declare a price the
same way. Stage 3.

## Stages

- **Stage 0** — [x] types + header codec + golden tests from the spec's
  own examples (needs okay-chain stage 0 for `Network`).
- **Stage 1** — [x] okay-http server gate over a remote `Facilitator`;
  client wrapper with a payment policy and a `Payer` trait; an
  end-to-end test against a fake facilitator.
- **Stage 2** — settlement followed with okay-chain `Tracker`; local
  `exact`/EVM verification (keccak, secp256k1, EIP-712 — priced as its
  own lane).
- **Stage 3** — MCP transport; a Cardano scheme only if x402 defines
  one (it has `exact` for EVM, SVM, Aptos, Sui as of the local clone).

## Decisions

- 2026-09-23 — **the codec is hand-written over `Json`, not a derived
  `Schema`.** x402 carries open JSON (`payload`, `extra`, `extensions`)
  and `Schema` has no case for an arbitrary JSON value; and x402 OMITS
  absent optionals where a derived encoder writes `null`.
- 2026-09-23 — **settle AFTER the route, and only a 2xx.** Settling
  first takes a payment for a failure; delivering before settling gives
  the resource away if settlement fails. The gate runs the route, keeps
  its answer, settles, and returns the answer only on success.
- 2026-09-23 — **replay is an atomic claim** on the payload, released
  when verification, the route or settlement fails — so a retry of an
  honest failure is not refused as a replay.

- 2026-09-23 — x402 sits ON okay-chain rather than beside it: its
  network, asset and amount types are okay-chain's, and confirming a
  settlement is the follower's job.
- 2026-09-23 — facilitator first, local verification later: the
  primitives for `exact`/EVM (keccak, secp256k1, EIP-712) do not exist
  in okay yet.

## Results

- okay-x402 landed stages 0–1 (2026-09-23), JVM and JS, 14 tests:
  the four headers of transports-v2/http.md decode and re-encode to
  the same JSON; the gate end to end in memory (unpaid 402, paid 200
  with `PAYMENT-RESPONSE`, a replay refused, the policy's limit, an
  invalid signature, a failing route not settled, a failed settlement
  withholding the answer); `HttpFacilitator` against a service built
  from the protocol's own shapes, an unreadable answer a refusal.
